# Release 0.80.1

## Scope

Version 0.80.1 validates per-object texture timing in multi-object export. One selected
object may export a texture sequence while sibling objects remain static in the same
atomic JSON and texture transaction.

## Standalone matrix

The Blender 5.2 headless acceptance covers Spine 3.8, 4.0, 4.1, 4.2, and 4.3 in both
Normal - UV Segments and Camera Projection.

Each case exports three objects at 128x128 with one Cycles sample:

- object A: two-frame sequence starting at frame 1;
- objects B and C: static textures evaluated at the current frame;
- four physical PNG files and one combined JSON per case.

The acceptance verifies legacy attachment swaps for Spine 3.8/4.0, native sequence
metadata for Spine 4.1+, and proves that static objects do not inherit sequence metadata
or animation timelines.

## Connected and mixed matrix

Spine 4.2 connected and mixed export is validated with both `3-Axis Rotation` and
`2-Axis Rotation + Scale`, and with both Normal - UV Segments and Camera Projection.

Connected cases contain one sequence object and one static object. Mixed cases contain a
two-object connected subgroup and one standalone object. The matrix validates both
possible mixed placements:

- sequence owner inside the connected subgroup;
- sequence owner inside the standalone subgroup.

Every other object remains static. Connected wrapper hierarchy, standalone subgroup
isolation, native Loop sequence ownership, attachment topology, output namespaces, and
Blender state restoration are checked for every case.

## UI and request contract

The existing Bake foldout already stores `Frames` and `Start` per selected Mesh object.
Version 0.80.1 adds executable coverage proving that these values remain independent
through object-profile capture and `A1MultiObjectSource` construction. A value of
`Frames = 0` remains static current-frame output; a positive value creates a Loop texture
sequence only for that object.

Public Export Selected Objects remains standalone-only. Connected and mixed composition
remain explicit development/API capabilities for Spine 4.2.

## Windows-safe atomic work paths

Blender and OpenImageIO may still reject temporary image paths near the traditional
Windows `MAX_PATH` boundary even when Python can resolve the same final output path.
The previous atomic stage name repeated the complete final stem and then appended a
long crash-recovery token. Long connected and mixed object names could therefore produce
a valid final PNG name but an invalid staged PNG path.

Version 0.80.1 derives a 248 UTF-16-code-unit transaction-work budget from the
traditional 260-unit Windows boundary minus twelve units of fixed safety headroom:

- readable historical work names remain unchanged while they fit;
- only the repeated final stem is compacted when the staged path would exceed the
  external-I/O budget;
- final JSON and PNG filenames are never shortened;
- compact names are unique by deterministic reservation index, without probabilistic
  hash collisions;
- durable journals retain the exact final, staged, and backup mapping;
- an output directory too deep even for the compact form fails before Blender bake or
  render with an explicit instruction to choose a shorter directory.

New transactions use a compact version 3 ownership token. It retains the complete
128-bit nonce and encodes the process ID and creation time in hexadecimal. The complete
process-start marker is represented by a fixed-size BLAKE2 digest, so PID reuse is still
detected without repeating the long platform marker in every work filename. Version 2
work tokens remain readable for stale-work recovery and direct metadata construction
remains version 2 compatible.

The connected/mixed Blender runners exercise long-name output shapes in both Normal - UV
Segments and Camera Projection. Their work paths must remain within the derived Windows
budget without changing user-facing output filenames.

## Preserved behavior

- Texture size in the new acceptance workers is 128x128.
- Cycles samples remain 1 for fast deterministic gates.
- Normal - UV Segments and Camera Projection remain separate explicit modes.
- Scene settings schema remains version 6.
- Unsupported target, profile, and composition combinations remain fail-closed.
- Source transforms, current frame, active object, selection, materials, Scene bake
  settings, render settings, Camera state, and temporary Blender datablocks must be
  restored after export.
