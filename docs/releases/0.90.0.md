# Release 0.90.0

## Scope

Version 0.90.0 extends **Depth Camera Projection** with a full angular parallax reserve.
The established public export modes remain:

```text
Normal / UV Segments
Camera Projection
Depth Camera Projection
```

Depth Camera Projection still uses the active Blender Perspective or Orthographic camera
as the setup/front view and retains one shared camera zero for every exported object. The
new reserve is opt-in and affects only Depth Camera Projection.

## Parallax Horizon Angle

The Rig foldout adds one public control:

```text
Parallax Horizon Angle
```

Blender stores the setting in radians and displays it in degrees. Its public range is
0–89°, with a 45° soft maximum.

The default is **0°**. At 0° the exporter preserves the complete 0.81.0 contract:

- only the active-camera front surface is retained;
- exactly one camera texture is rendered per texture frame;
- exactly one weighted mesh attachment is emitted as `<object>_Segment_0`;
- no parallax reserve slots, images, or output paths are created.

A positive angle retains connected source surface behind the current camera horizon. The
value is not a polygon count and therefore does not depend on mesh tessellation density.

## Angular surface expansion

The evaluated source mesh is triangulated and represented as shared-edge adjacency.
Current front-most camera-visible triangles are the zero-cost seeds. Crossing one shared
edge adds the unsigned dihedral angle between the two triangle planes. A deterministic
Dijkstra traversal retains every connected triangle whose minimum accumulated cost does
not exceed Parallax Horizon Angle.

Consequently, the same physical 30° bend is retained at 30° whether it is represented by
one large polygon or many coplanar subdivisions. Disconnected geometry is never reached
through angle expansion. Existing active-camera clipping remains local: fully visible
front polygons stay unchanged, fully invisible front polygons are omitted, and only
polygons intersecting the camera frame are clipped and locally retriangulated.

## Shared front and reserve rig

Front and reserve surfaces are combined into one union MeshSnapshot before Z-group and
vertex-bone construction. The union is the only owner of camera-distance vertex lineage.
Every front or reserve attachment refers back to that shared vertex namespace.

This produces one common two-axis depth rig:

- the active camera remains global depth zero;
- all retained points store positive camera distance;
- front and reserve attachments reuse the same generated vertex bones;
- reserve geometry does not duplicate the complete rig;
- **Max Depth Points** limits the combined front plus reserve point count.

When a requested horizon cannot fit within Max Depth Points, readiness/export fails with
a structured diagnostic. It never silently reduces the requested angle or replaces the
object with an unrelated whole-object grid.

## Virtual texture coverage

A positive reserve uses eight deterministic virtual camera directions around the active
camera setup view:

```text
RIGHT
UP_RIGHT
UP
UP_LEFT
LEFT
DOWN_LEFT
DOWN
DOWN_RIGHT
```

Each reserve triangle is assigned to the direction that best exposes its camera-space
surface orientation. Virtual cameras orbit around the projected Blender Object Origin by
the requested angle. They retain the active camera projection kind, clip planes, render
resolution, materials, lighting policy, and sequence timing.

Every virtual view is fitted so the evaluated source remains inside its render:

- Perspective views reduce the temporary proxy-camera lens when necessary;
- Orthographic views increase the temporary proxy-camera ortho scale when necessary.

Only temporary camera proxies receive the virtual transform and fit. Source Objects,
source Meshes, active-camera Objects, camera datablocks, animation data, constraints,
selection, current frame, and Scene settings remain protected by the existing
transactional state guards and are restored in `finally`.

## Reserve attachments and draw order

Only virtual views that own retained reserve polygons produce outputs. Every used view
creates:

- one independent camera texture or texture sequence;
- one independent Spine weighted mesh attachment;
- one stable slot/attachment namespace:

```text
<object>_Parallax_<VIEW>
```

Reserve slots are emitted before the established front slot in Spine draw order. The
front attachment `<object>_Segment_0` is emitted last and remains visually authoritative
at the setup pose. Reserve layers become visible only where X/Y pseudo-rotation reveals
surface beyond the front horizon.

No `<object>_Segment_1` is created by the reserve feature.

## Per-view crop and UV

Every virtual view owns its own alpha-union crop. Its reserve polygons receive full-frame
UV from that same fitted virtual projection, then post-render finalization converts only
that attachment to its corresponding crop-local UV.

The front crop is never applied to reserve UV and reserve crops are never applied to the
front attachment. Crop conversion preserves weighted vertices, triangles, hull indices,
bone indices, and sequence metadata.

If rendered alpha does not cover a retained reserve UV, finalization fails with a
structured diagnostic instead of clamping an unrelated transparent pixel into the mesh.
Opaque or correctly alpha-covered source materials are therefore required for visible
reserve surface.

## Atomic output transaction

Front and all reserve images are staged in the same AtomicFileTransaction as the Spine
JSON. Any geometry, render, crop, UV, serialization, or commit failure rolls back the
complete object or multi-object output set. JSON cannot be committed while one referenced
reserve image is missing.

Realized multi-object output validation includes all geometry-dependent reserve plans and
rejects Windows case-folded path collisions before staging.

## Sequences

Each used reserve view inherits the front plan's frame tasks and material evaluation
schedule. A two-frame Depth sequence therefore renders two front textures and two textures
for every retained reserve view. Timeline advancement remains material-only: Blender
object motion and active-camera animation are not baked into either front or reserve
sequence geometry.

## Scene migration

Scene settings schema is **8**. Existing `.blend` files receive:

```text
Parallax Horizon Angle = 0°
```

The migration initializes only missing values and does not overwrite existing Depth,
Normal / UV Segments, Camera Projection, Spine target, rig, or output choices.

## Validation matrix

The 0.90.0 acceptance matrix includes:

- immutable 0° front-only compatibility;
- angular expansion above and below a known shared-edge bend;
- tessellation-density independence for the same physical bend;
- deterministic reserve face and virtual-view ownership;
- combined Max Depth Points enforcement;
- Perspective and Orthographic virtual camera fitting;
- unique static and sequence output namespaces for every used view;
- shared union Z-group and generated vertex-bone lineage;
- reserve slots below the front slot in draw order;
- view-owned crop-local UV and physical PNG coverage;
- single-object and standalone multi-object export;
- active-camera/source state restoration after success and failure;
- Spine JSON targets 3.8, 4.0, 4.1, 4.2, and 4.3;
- Blender 5.2 extension validation, isolated installation, enable, smoke, disable, and
  uninstall.

## Compatibility

- Blender minimum: 5.2.0.
- Scene settings schema: 8.
- Existing `Normal / UV Segments` behavior is unchanged.
- Existing flat `Camera Projection` behavior is unchanged.
- `Depth Camera Projection` with Parallax Horizon Angle 0° preserves 0.81.0 output.
- Spine JSON target selection remains 3.8.99, 4.0.64, 4.1.24, 4.2.43, or 4.3.23.
