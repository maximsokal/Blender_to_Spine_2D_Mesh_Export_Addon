# Testing and Release Validation

## Current candidate

The current extension candidate is **0.47.11**.

Supported production target scope:

- Spine 4.2.43 remains the primary full JSON target.
- Spine 4.1.24 is enabled only for `2-Axis Rotation + Scale` in single-object and standalone multi-object exports.
- Production **Export Selected Objects** always builds a standalone multi-object plan.
- Persisted hidden Connect flags from older `.blend` files are ignored by production Analyze/Export.
- Connected and mixed composition remain development-only internal capabilities.
- Spine 4.1 connected, mixed, and 3-Axis requests remain fail-closed before Blender geometry work.

A focused run is not a release gate. Every required validation layer must pass on the same commit, and every runtime claim must use JSON generated by that exact commit.

## Validation layers

The repository uses five validation layers:

1. Blender-independent tests in `tests/`.
2. Real `bpy` tests in `tests_bpy/`.
3. Blender 5.2 headless integration scripts in `tests/blender_headless/`.
4. Exact Spine runtime probes for target-specific behavior.
5. Blender extension validation, isolated installation, and ZIP packaging.

## Spine 4.1 Blender-to-runtime acceptance

The acceptance wrapper creates three independent real Blender Mesh objects, exports them through the production standalone multi-object service, and invokes the exact read-only Spine 4.1 runtime oracle.

```powershell
$RuntimeEntry = "E:\muse\Spine2D_curve_optimization\Spine2D_curve_optimization\vendor\spine-webgl-41\index.js"
$OutputRoot = "E:\test_BtSe\spine41_blender_pipeline_0.47.11"

python `
    tools\run_spine41_standalone_acceptance.py `
    --blender $Blender `
    --runtime-entry $RuntimeEntry `
    --output-root $OutputRoot `
    --replace-output

if ($LASTEXITCODE -ne 0) {
    throw "Spine 4.1 standalone acceptance failed"
}
```

Required markers:

```text
[SPINE41_STANDALONE] PASS production multi-object export
SPINE41_STANDALONE_ACCEPTANCE=PASS
```

The external runtime repository is read-only input. The acceptance tool must not clone, install into, delete from, or modify that repository.

## Persisted Connect regression

Install the candidate, open a `.blend` previously saved with Object Connect values enabled, select several meshes, and run **Export Selected Objects** for Spine 4.1.24.

Required result:

- export mode is standalone;
- no `CONNECTED_MULTI_OBJECT` capability error appears;
- no `all_objects_*` bones or constraints appear in JSON;
- each object keeps its independent main and control rig.

The old Object property may remain serialized for backward compatibility, but it must not influence production routing.

## Release evidence

A release claim must record:

- exact candidate commit SHA;
- clean working tree or exact local modifications;
- Python, Blender, Node, Spine Editor, and runtime versions;
- complete pytest summary;
- real-bpy summary;
- required Blender-headless markers;
- runtime oracle and scale-response reports;
- persisted Connect regression result;
- package build and isolated install results;
- final ZIP path, size, timestamp, and SHA-256;
- fresh manual Blender-to-Spine import results for representative assets.

Do not state that a gate passed without its corresponding log. Do not reuse results from an older commit.

## Failure handling

When a test fails:

1. preserve the complete traceback;
2. identify the production owner or stale contract;
3. fix the owning implementation rather than weakening an unrelated test;
4. rerun the focused failure;
5. rerun the complete affected layer;
6. rerun downstream Blender, runtime, and packaging gates when production behavior changed.
